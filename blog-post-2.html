CI/CD avec GitHub Actions : Guide complet

22 octobre 2024 · 12 min de lecture

GitHub Actions est un outil de CI/CD intégré directement dans GitHub, qui permet d'automatiser vos workflows de test et de déploiement sans configuration d'infrastructure tierce. Dans ce guide, nous allons construire un pipeline complet.

Concepts fondamentaux

Avant de commencer, clarifions les concepts clés :

  • Workflow : un processus automatisé défini dans un fichier YAML sous .github/workflows/
  • Job : un ensemble d'étapes qui s'exécutent sur le même runner
  • Step : une tâche individuelle au sein d'un job (commande shell ou action)
  • Action : une tâche réutilisable publiée sur le GitHub Marketplace
  • Runner : la machine virtuelle qui exécute le job

Structure d'un workflow

# .github/workflows/ci.yml
name: Pipeline CI/CD          # Nom affiché dans l'interface

on:                           # Déclencheurs
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:                          # Variables d'environnement globales
  NODE_VERSION: '20'

jobs:
  test:                       # Premier job : tests
    name: Tests unitaires
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'
      - run: npm ci
      - run: npm test

  build:                      # Second job : build (dépend de test)
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

Jobs parallèles et matrice

La stratégie matrix permet d'exécuter le même job sur plusieurs configurations en parallèle :

jobs:
  test-matrix:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [18, 20, 22]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci && npm test

Gestion des secrets

Les informations sensibles (clés API, tokens) ne doivent jamais être en dur dans le code. Utilisez les secrets GitHub :

  1. Allez dans Settings → Secrets and variables → Actions
  2. Cliquez sur New repository secret
  3. Référencez-les dans votre workflow avec ${{ secrets.NOM_DU_SECRET }}
- name: Deploy to AWS
  env:
    AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
    AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
  run: aws s3 sync ./dist s3://mon-bucket

Déploiement avec environnements

Configurez des environnements avec des validations manuelles pour les déploiements sensibles :

jobs:
  deploy-prod:
    needs: [test, build]
    runs-on: ubuntu-latest
    environment:
      name: production         # Environnement avec approbation requise
      url: https://myapp.com
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist
      - name: Deploy
        run: ./scripts/deploy.sh production
💡 Astuce : utilisez concurrency pour annuler automatiquement les workflows en cours lors d'un nouveau push sur la même branche, évitant ainsi les déploiements superposés. 
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

Optimisation du cache

La mise en cache des dépendances réduit drastiquement le temps d'exécution :

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: ${{ runner.os }}-node-

Conclusion

GitHub Actions offre une flexibilité remarquable pour construire des pipelines CI/CD robustes. La clé est de commencer simple (lint → test → build) et d'ajouter progressivement : déploiements multi-environnements, notifications, sécurité (SAST/DAST), et reporting de couverture.
