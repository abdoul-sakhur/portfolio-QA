Écrire quelques tests avec Playwright est relativement simple. Concevoir un framework capable d'évoluer avec une application métier est une toute autre histoire.

Dans le cadre d'un projet de tests automatisés pour une application de la Direction Générale des Impôts (DGI), l'objectif n'était pas uniquement d'automatiser des scénarios, mais de construire une base solide permettant aux équipes QA et développement de travailler efficacement sur le long terme.

Une architecture pensée pour évoluer

L'une des premières décisions a été d'adopter le Page Object Model (POM). Ce pattern permet d'isoler les interactions avec l'interface utilisateur dans des classes dédiées.

L'organisation du projet est volontairement simple.

playwright/
│
├── pages/
│   ├── connexion.page.ts
│   ├── inscription.page.ts
│   └── sideMenu.page.ts
│
├── specs/
│   ├── connexion.spec.ts
│   ├── inscription.spec.ts
│   └── dossier-creation.spec.ts
│
├── utils/
├── conf/
├── scripts/
└── playwright.config.ts

Grâce à cette séparation, une modification de l'interface n'impacte généralement que les objets de page, sans nécessiter une réécriture complète des scénarios.

Encapsuler les actions dans les Page Objects

Plutôt que de manipuler directement les sélecteurs dans les tests, toutes les actions sont regroupées dans des classes.

export class ConnexionPage {

    constructor(private page: Page) {}

    async seConnecter(email: string, password: string) {

        await this.page.fill('#email', email);
        await this.page.fill('#password', password);
        await this.page.click('button[type="submit"]');

    }

}

Le scénario devient alors beaucoup plus lisible.

test("Connexion utilisateur", async ({ page }) => {

    const connexion = new ConnexionPage(page);

    await connexion.seConnecter(email, password);

});

Le test décrit le comportement attendu tandis que la logique technique reste centralisée dans les Page Objects.

Centraliser les configurations

Les identifiants et les URLs ne sont jamais codés directement dans les scénarios.

conf/
│
├── credentials.conf.json
├── credentials.ts
└── environement/
    └── lien.conf.json

Les variables d'environnement sont ensuite chargées automatiquement.

APP=DGI
ENV=staging

JIRA_HOST=xxxxx.atlassian.net
PROJECT_KEY=SCRUM

Cette approche permet de changer facilement d'environnement sans modifier le code.

Exécuter les tests simplement

Le framework propose plusieurs modes d'exécution.

Lancer toute la suite :

npm run test

Lancer uniquement les tests Smoke :

npm run test:smoke

Exécuter un scénario précis :

bash scripts/playwright_launch_test.bash \
DGI/connexion.spec.ts

Ou encore filtrer un test particulier :

npx playwright test \
--grep "Connexion utilisateur"

Cette flexibilité facilite les validations rapides pendant le développement.

Générer automatiquement les rapports Allure

Chaque campagne de tests produit un rapport Allure contenant :

  • les captures d'écran ;
  • les traces Playwright ;
  • les statistiques d'exécution ;
  • les scénarios réussis et échoués.

La génération du rapport reste très simple.

npm run allure:report

Disposer immédiatement d'un historique des exécutions accélère considérablement l'analyse des campagnes de tests.

Intégrer le framework dans Jenkins

L'automatisation prend tout son sens lorsqu'elle est exécutée dans une chaîne CI/CD.

Voici un exemple simplifié de pipeline.

pipeline {

    agent any

    stages {

        stage('Install') {

            steps {
                sh 'npm install'
            }

        }

        stage('Tests') {

            steps {
                sh 'npm test'
            }

        }

    }

}

Les campagnes peuvent ainsi être exécutées automatiquement à chaque commit ou avant chaque livraison.

Sécuriser les secrets Jenkins

Une erreur fréquente consiste à stocker les tokens directement dans le dépôt Git.

La bonne pratique consiste à utiliser le Credentials Store de Jenkins.

environment {

    JIRA_EMAIL = credentials('jira-email')

    JIRA_API_TOKEN = credentials('jira-api-token')

}

Les secrets restent invisibles dans les logs et ne transitent jamais dans le code source.

Créer automatiquement les tickets Jira

Le framework est capable de créer un ticket Jira lorsqu'un scénario échoue.

Avant toute création, une requête JQL est exécutée afin de vérifier si un ticket similaire existe déjà.

project = "SCRUM"

AND summary ~ "Connexion utilisateur"

AND status NOT IN (Done, Closed)

AND labels = automation

Si un ticket est déjà ouvert, aucune nouvelle anomalie n'est créée.

Cette stratégie réduit considérablement les doublons dans les projets où plusieurs pipelines exécutent les mêmes campagnes de tests.

Le flux d'exécution

Une campagne suit toujours le même cycle.

Playwright
        │
        ▼
Chargement de la configuration
        │
        ▼
Initialisation du navigateur
        │
        ▼
Exécution des hooks
        │
        ▼
Page Objects
        │
        ▼
Assertions
        │
        ▼
Rapport Allure
        │
        ▼
Création automatique du ticket Jira

Cette chaîne garantit une exécution reproductible aussi bien en local que sur Jenkins.

Conclusion

Un framework Playwright ne doit pas seulement exécuter des tests. Il doit être capable d'accompagner l'évolution d'une application pendant plusieurs années.

L'utilisation du Page Object Model, d'une architecture modulaire, de rapports Allure, d'une intégration Jenkins et d'une création intelligente des tickets Jira permet de transformer une simple suite de tests en une véritable plateforme d'assurance qualité.

Au final, l'objectif n'est pas d'avoir le plus grand nombre de scénarios automatisés, mais de disposer d'un framework fiable, lisible et suffisamment robuste pour évoluer au même rythme que l'application qu'il valide.
